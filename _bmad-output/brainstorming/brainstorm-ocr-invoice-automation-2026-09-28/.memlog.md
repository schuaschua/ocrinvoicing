- (direction) Context: retail sport-shoe chain, thousands of supplier material invoices/month; many are phone photos shared via WhatsApp, manually extracted, keyed, sent to existing accounts system
- (decision) Stance: Creative Partner; coach chooses 2 techniques: Assumption Reversal, then Morphological Analysis
- (technique) started Assumption Reversal
- (idea by user) Reverse 'the invoice is genuine': assume any invoice could be fake — build fraud/authenticity checking into intake
- (idea by coach) Zero-trust intake: invoice only accepted if it matches a real PO + goods-received record; the photo proves nothing on its own
- (idea by user) Fraud vector: photo edited before sending (amounts/details tampered)
- (idea by user) Fraud vector: same invoice submitted more than once (duplicate)
- (question) User unsure how edited photos / duplicates could be detected
- (idea by coach) Duplicate catch: fingerprint each invoice by supplier + invoice no. + amount + date, plus perceptual image hash to catch re-photographed copies
- (idea by coach) Edit catch: compare extracted amounts vs PO price x received qty; flag mismatch instead of trying to detect pixel edits
- (idea by user) Honest-error vector: supplier gives wrong supplier ID and manual keying doesn't catch it
- (idea by user) Impersonation vector: fake/hijacked WhatsApp accounts sending fake invoice data
- (question) User unsure what attacker would gain from fake WhatsApp invoices
- (insight by coach) Main payoff for impersonators is payment redirection: invoice shows changed bank details so real supplier's payment goes to fraudster
- (idea by coach) Supplier ID is derived by the system (registered sender number + vendor master match), never taken from what's written on the invoice
- (idea by coach) Bank-detail change on an invoice never auto-posts; triggers call-back to supplier's number on file
- (idea by user) Replace WhatsApp with a mobile web page where suppliers upload the invoice photo
- (idea by coach) Upload page shows extracted fields back to supplier instantly for confirmation — supplier fixes errors (wrong supplier ID etc.) before submission
- (idea by coach) Personal per-supplier upload link/login solves impersonation: identity comes from the link, not a phone number
- (insight by user) Supplier self-correction is a risk: suppliers could lie when 'fixing' extracted data
- (decision) User likes personal per-supplier upload link
- (idea by user) Invoice should carry a delivery date
- (idea by user) Match photo-taken date against delivery date; on mismatch trigger a message to the user
- (idea by coach) Keep original OCR read + supplier's edits side by side; any supplier change to amounts/bank/qty is flagged for review, cosmetic fixes pass
- (idea by coach) Use server-side upload timestamp (not only photo EXIF, which can be stripped/faked) as the trusted 'photo taken' time
- (idea by coach) Three-date truth for vendor speed: promised date (PO) vs delivery date on invoice vs goods-received date from own warehouse
- (direction) Correction: date-mismatch message goes to an admin review queue, not to the supplier/user
- (decision) Rejected: supplier editing/confirming extracted data — suppliers cannot edit; system trusts what it reads from the photo
- (decision) Rejected: upload-timestamp-over-EXIF idea — trust the photo date
- (decision) Rejected: early-warning / predict-late-shipments direction — too complicated
- (decision) Three-date check (PO promised vs invoice delivery vs goods received) kept as a could-have feature
- (direction) User prefers keeping things simple; avoid over-complicated mechanisms
- (idea by user) Early late-shipment signal: PO has expected date (e.g. PO 1 Jan, expected 7 Jan) but no invoice photo arrives until much later — missing invoice past expected date = likely late
- (decision) All invoices auto-processed into accounts system unless OCR confidence in extraction is low
- (idea by coach) Overdue-invoice list: daily list of POs past expected date with no invoice yet, grouped by supplier — the slow-vendor analysis comes free
- (idea by coach) Per-field confidence: admin sees only the photo crop + the uncertain field(s) to fix, not the whole invoice
- (idea by user) Overdue list auto-sends a reminder notification to the supplier via the supplier upload app
- (idea by user) Compare vendors on price for the same materials using posted invoice data
- (idea by coach) Price-creep alert: flag when a supplier's unit price for the same material rises vs their own last N invoices
- (idea by coach) Supplier scorecard combining price + speed per material — who's cheapest vs who's fastest
- (idea by user) Freed-up admins redeployed to other manual-work functions such as sales; small team remains for flagged invoices
- (technique) started Morphological Analysis — parameters: capture, extraction, validation, integration, analytics/alerts
- (direction) Constraint: existing accounts system has an API we call to pass data; accepts XML only
- (idea by coach) Integration: translator layer converts validated invoice (internal JSON) into the accounts XML and calls the API; rest of pipeline never touches XML
- (idea by coach) Integration: retry queue — if accounts API is down or rejects, invoice waits and retries; after N failures goes to admin queue with the API error
- (idea by user) Capture: paper invoices must be supported
- (idea by user) Capture: scanned PDF invoices must be supported
- (idea by coach) Warehouse scan station: paper invoice arriving with goods is photographed/scanned at goods-in, linked to the delivery on the spot
- (idea by coach) Upload page accepts PDF as well as photo; everything lands in one intake queue so extraction is channel-agnostic
- (idea by user) Extraction challenge: handwriting on invoices
- (idea by user) Extraction challenge: blurry phone photos
- (idea by user) Extraction challenge: company logos (identify supplier / avoid misreading)
- (idea by user) Extraction challenge: many different invoice formats/layouts across suppliers
- (idea by coach) Blur check at upload: page rejects too-blurry/dark/cropped photo instantly and asks for a retake before submit
- (idea by coach) Use AI vision model (reads layout like a human) rather than template OCR, so new supplier formats work without setup
- (idea by coach) Learn from admin fixes: each correction improves reading of that supplier's format next time
- (idea by user) Use company logo on invoice to recognise the supplier automatically
- (idea by coach) Logo vs upload-link cross-check: logo says supplier A but uploaded via supplier B's link -> flag to admin (catches wrong supplier ID / impersonation)
- (direction) Analytics audience: finance team and procurement
- (idea by coach) Procurement view: before placing a PO, show supplier's on-time rate + price trend for that material right in the ordering flow
- (idea by coach) Finance view: monthly spend by supplier, price-creep alerts, duplicate/flagged invoice counts
- (idea by user) Bad supplier score triggers a conversation with the supplier
- (idea by user) At the same time management searches for alternative suppliers
- (idea by user) 'Bad' definition: multiple price increases within a year
- (idea by user) 'Bad' definition: slow service (late deliveries)
- (idea by user) 'Bad' definition: big price difference vs other suppliers for the same material
- (idea by coach) Supplier watchlist: auto-adds a supplier when any of the 3 'bad' rules trips, notifies procurement + management with the evidence (invoices, dates, price history)
- (idea by coach) Alternative-supplier shortlist: when a supplier hits watchlist, show other suppliers already invoicing the same material, ranked by price + speed
- (decision) Scope: build ALL options across all five rows (capture, extraction, validation, integration, analytics) — no minimal-first slice; three-date check remains could-have
- (decision) Dropped: logo-based supplier recognition (and with it the link-vs-logo cross-check)
- (decision) Out of scope: what happens to freed-up admins (redeploy or let go) — not a concern of this project
- (decision) All other ideas matter and are in scope
- (insight) Synthesis: (1) personal supplier upload link is the load-bearing idea — fixes identity/impersonation and wrong supplier IDs, is the channel for overdue reminders, and records when invoices arrive; (2) the PO is the spine — amount check vs edited photos, expected date for overdue list, price baseline for comparison all hang off PO data, so PO access is the key dependency; (3) one dataset serves both goals — invoice arrival vs PO expected date is simultaneously the chase list and the vendor-speed analytics; (4) single admin queue is the only human touchpoint — low confidence, duplicates, date mismatch, API failures all land there; everything else flows straight to accounts XML API. Chosen direction: build all of it (minus logo), three-date check as could-have.
