- (decision) Why: pain — sport-shoe retail chain gets thousands of supplier material invoices/month, many as WhatsApp phone photos, manually extracted and keyed into accounts system; plus opportunity — use invoice data to spot slow/expensive suppliers
- (capability) CAP-1 Supplier submits invoice photo or PDF from phone via personal per-supplier upload link; supplier identity comes from the link; supplier cannot edit extracted data
- (capability) CAP-2 Paper invoices arriving with goods are photographed/scanned at warehouse goods-in and linked to that delivery
- (capability) CAP-3 Upload rejects too-blurry/dark/cropped photos immediately and asks for retake
- (capability) CAP-4 Invoice fields extracted from any supplier layout, including handwriting, with per-field confidence; new supplier formats work without per-supplier setup
- (capability) CAP-5 Extracted amounts checked against PO price x received quantity; mismatch goes to admin queue
- (capability) CAP-6 Duplicate invoices detected (supplier + invoice no. + amount + date fingerprint, plus image similarity for re-photographed copies); duplicates go to admin queue
- (capability) CAP-7 Photo-taken date checked against invoice delivery date; mismatch goes to admin queue (not to supplier)
- (capability) CAP-8 Invoice whose bank details differ from supplier master is held; admin verifies via call-back to supplier number on file
- (capability) CAP-9 Single admin queue receives every exception (low confidence, PO mismatch, duplicate, date mismatch, bank change, supplier-ID mismatch, API failure); admin sees photo crop + flagged fields and resolves
- (capability) CAP-10 Admin corrections improve future extraction for that supplier's format
- (capability) CAP-11 Invoices passing all checks auto-post to accounts system via its XML API; failed calls retry, then go to admin queue with the API error
- (capability) CAP-12 Daily overdue list: POs past expected date with no invoice received, grouped by supplier
- (capability) CAP-13 Overdue POs automatically trigger a reminder to the supplier via the upload app
- (capability) CAP-14 Price comparison across suppliers for the same material, plus price-creep alert when a supplier's unit price rises vs its own recent invoices
- (capability) CAP-15 Supplier watchlist: supplier auto-added when any rule trips (multiple price increases within a year, slow deliveries, large price gap vs other suppliers for same material); procurement + management notified with evidence to start supplier conversation
- (capability) CAP-16 When a supplier is watchlisted, show alternative suppliers already invoicing the same material, ranked by price and speed
- (capability) CAP-17 Procurement sees supplier scorecard (on-time rate, price trend per material) when deciding an order
- (capability) CAP-18 Finance sees monthly spend by supplier, price-creep alerts, and flagged/duplicate invoice counts
- (capability) CAP-19 (could-have) Three-date check per delivery: PO promised date vs invoice delivery date vs goods-received date
- (constraint) Accounts system accepts data only through its API, XML only
- (constraint) Suppliers cannot edit or confirm extracted data; system trusts what it reads from the document (user rejected supplier self-correction: suppliers could lie)
- (constraint) Photo date is trusted as the photo-taken date; no server-timestamp substitution (user rejected)
- (constraint) Supplier identity comes from the personal upload link (or warehouse delivery link), never from supplier ID written on the invoice
- (constraint) Every invoice auto-posts unless a check flags it; the admin queue is the only human touchpoint
- (constraint) Late-shipment signal is rule-based (no invoice by PO expected date); no predictive modelling (user: too complicated, keep simple)
- (constraint) Volume: thousands of invoices per month
- (constraint) Scope: all capabilities built; no minimal-first slice (user decision); CAP-19 is could-have
- (decision) Non-goal: logo-based supplier recognition and link-vs-logo cross-check (dropped by user)
- (decision) Non-goal: supplier editing/confirmation of extracted data
- (decision) Non-goal: predicting late shipments beyond the overdue rule
- (decision) Non-goal: redeployment or staffing of freed-up admins
- (decision) Non-goal: changing the accounts system itself
- (assumption) WhatsApp intake is retired in favour of the upload link; user proposed the page in answer to 'what if WhatsApp weren't the channel' but did not state a transition plan
- (assumption) Upload page is a mobile web page reached by link (user said 'a page on mobile'; later called it 'the suppliers app')
- (assumption) PO data and goods-received records exist in a system the solution can read (needed by CAP-5, CAP-12, CAP-19)
- (assumption) Supplier master holds bank details and phone number on file (needed by CAP-8)

- (question) What OCR confidence threshold sends a field to the admin queue?
- (question) How long after PO expected date is an invoice overdue (grace period), and how often are supplier reminders repeated?

- (question) How are personal upload links issued, revoked and protected if a link is shared or leaked?
- (question) What measurable target defines success (e.g. % auto-posted without admin touch, time from upload to posting)?
